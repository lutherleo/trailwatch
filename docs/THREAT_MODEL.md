# Threat model

## Scope and purpose

trailwatch is a **defensive** detector for AWS identity misuse visible in CloudTrail management
events. It is a research tool: it reads logs, it never calls AWS APIs, never changes
anything in an account, and all bundled data is synthetic. The simulator produces log records
describing attacks; it contains no exploit code and interacts with no system.

## Assets

* The AWS account's identities (IAM users, roles, SSO sessions, root) and what they can do.
* The audit trail itself (CloudTrail, GuardDuty, Config), which attackers try to blind.

## Adversaries in scope

| adversary | entry | what trailwatch looks for |
|---|---|---|
| External actor with a leaked long-term access key | key in a repo, laptop malware, CI logs | new country/ASN/UA family, impossible travel, discovery bursts, new regions, compute abuse APIs |
| Phished console password on a user without MFA | credential phishing | no-MFA sign-in followed by IAM writes, backdoor users and keys |
| Actor with a stolen role session (CI/CD, workload) | exposed runner, SSRF to metadata service | key creation for other principals by a role, new networks for an automation role |
| Any of the above trying to blind defenders | after initial access | CloudTrail stop/delete/weakening, GuardDuty and Config tampering, flow-log deletion |
| Insider or actor living inside the workload's network and tooling | compromised host | only weak novelty signals; **largely out of reach** (the `low_and_slow` scenario measures this gap) |

## Trust assumptions

* CloudTrail records are authentic and complete for management events (log file integrity
  validation and an organization trail in a separate account are assumed, not checked).
* The IP-to-network map is accurate. The bundled map is synthetic; on real data a real map must
  be supplied or the network-based rules are blind.
* Event time is trustworthy to within the reorder buffer's lateness (15 min by default).

## Attacks on the detector itself and mitigations

| attack | effect | mitigation / status |
|---|---|---|
| Baseline poisoning: act slowly so malicious behaviour becomes "familiar" | suppression of later activity | decay limits how long anything stays familiar; warm-up delays novelty; **not fully mitigated** (no frozen trusted baseline) |
| Evasion by mimicry: use the victim's network, region, UA family | no novelty signals | stateful rules (no-MFA IAM changes, key creation, tampering) do not depend on novelty; insider-style mimicry is a documented gap |
| VPN through the victim's usual egress | impossible-travel suppression | travel rule only suppresses when *both* networks are familiar; new hosting/VPN ASNs still trigger novelty |
| Alert flooding to exhaust analysts | many alerts | dedup per rule/principal/key with TTL; risk alerts fold into open alerts |
| State exhaustion with many principals or calls | memory growth / OOM | every table is capped (LRU or top-K); windows are item-capped; the benchmark shows flat memory from 1k to 60k principals |
| Malformed or hostile log records | crash, parser confusion | strict parsing of required fields, lenient elsewhere; failures are counted and skipped, never fatal; typed config rejects unknown keys |
| Disabling logging so there is nothing to detect | blind detector | the tampering events themselves are critical alerts; a gap in delivery is **not** detected (no heartbeat check) |
| Replay / duplicate delivery | double counting | duplicate `eventID`s are dropped (bounded LRU of recent ids) |

## Out of scope

* Data events (S3 object reads, Lambda invokes), network-level telemetry, endpoint telemetry.
* Detection across multiple accounts or an AWS Organization as a whole.
* Response actions (key deactivation, session revocation): trailwatch only emits alerts.
* Any offensive capability: the simulator writes log records, nothing else.

## Data handling

The bundled datasets contain no real identities, IPs, account ids or credentials: account
`111122223333` is the AWS documentation placeholder, IPs are reserved ranges, key ids are random
strings with an `AKIA`/`ASIA` prefix generated by a seeded RNG. Real logs fed to the CLI stay
local; alerts contain principal ARNs and source IPs and should be handled as sensitive.
